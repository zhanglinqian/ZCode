# 架构治理与工程化说明

> 范围：architecture-policy 治理、根命令、lint/format/typecheck/knip、测试现状、构建与发行、第三方声明。代码基准：main@a4b44451（v4.0.0）；核对日期：2026-11-25。

## 架构治理（architecture-policy.yaml）

- 可执行策略在根 `architecture-policy.yaml`：**149 个模块**（rpc/shared/provider/provider-node/services/session/storage/client/server/zcode-server-cli/ui/web/desktop/formal-proof/zcode-cli，以及 v3.15.1 起陆续新增的 session-control、app-control、plugin-api、design-runtime、stream-animate、e2e-report 等），其中 **133 个 `managed: true`**、16 个 `managed: false`（存量未接管模块，如 session、stream-animate、e2e-report）；另有 **105 条 `exceptions`** 登记逐项豁免（多为「本次上游整合保留既有实现，不为行数机械拆分」的 `*-edit` / `*-existing-edit` 条目）。
- storage 仍是最早一批受管模块（layers: domain→app→adapters，publicEntrypoints: `packages/services/src/storage/contract.ts`，owner: desktop-settings）；session-control、app-control、app-control-protocol、cli-session-control-* 系列是 v3.18.0 起新增的受管边界（owner 分别为 conversation / agent）。
- **owner 分布**（按模块数）：conversation 37、agent 23、plugin 18、desktop 18、remote 12，其余 persistence / cli / runtime / identity / web 等各 1–3 个。
- session 模块现为 `managed: false`，声明 6 个 publicEntrypoints（`contract.ts`、`taskIndexRepo.ts`、`automationRepo.ts`、`offPeakTaskRepo.ts`、`tasksDatabase/migrations.ts`、`tasksDatabase/prepared.ts`），其中 **`contract.ts` 仍不存在**（见 [../代码不规范清单.md](../代码不规范清单.md)）。
- global 约束：`maxFileLines: 800`（v3.14.3 时为 400）、`maxContractLines: 300`、`maxPublicMethods: 12`、`forbidCycles`、`forbidDeepImports`、`managedOnly: true`；新增 `newFilesEnforcedSince: "2026-09-10"`（`unmanaged-new-file` 规则只约束此日期后首次入库的文件）、`acceptedUpstreamCommits`、`acceptedUpstreamSnapshot: scripts/architecture/upstream-snapshot.json`。
- 命令：`pnpm architecture:check [-- --changed]`、`architecture:report`、`architecture:baseline:update`（仅评审后的有意变更可刷新基线，CI 不自动刷）、`architecture:context <module-id>`（生成模块受控阅读包）、`architecture:adopt`（把存量目录登记为受管模块，参见 `windows-runtime-host` 模块注释）。
- 治理工作流（`.agents/skills/architecture-governance/SKILL.md`）：改代码前 `architecture:check --changed` 定位模块 → `architecture:context` 读契约 → 先写 spec 再实现（单一 owner、单一路径、显式分层与边界、显式时序）→ 改后再 check，新违规与基线违规分开报告。
- 分层速查：domain 纯（无 IO、无 await 世界）；app 经 ports 决定副作用；adapters 执行 IO；跨模块边只走 public contract。
- 受管模块必需文件为 `module.ts`、`contract.ts`、`contract.example.ts`、`CONTRACT.md`；架构检查**不再要求或自动生成 `contract.test.ts`**（App 业务单测已退役，见下文「测试现状」）。

## 测试现状（以目标包 package.json 与实际文件为准）

- **工程 Vitest**：根 `vitest.config.ts` 只注册两个 project——`engineering`（显式清单 `scripts/engineering-test-files.json`，182 条；`pool: "forks"`、`fileParallelism: false`、`maxWorkers: 1`）与 `packages/zcode-cua/vitest.config.ts`。**禁止重新使用 `packages/*/test` 的业务单测通配符**。

- `pnpm bootstrap`（安装 + 桌面本地资源 + build:bootstrap）；`bootstrap:with-remote` 加远程资源（mock-cdn）。
- 桌面打包 `pnpm bundle:desktop`（细节见 [../桌面应用/构建与打包说明.md](../桌面应用/构建与打包说明.md)）。
- 命令行发行包 `pnpm build:zcode`（`scripts/build-zcode.mjs`）：构建 CLI/TUI、后端、Web → 收集原生库/worker/运行时依赖 → 组装 `dist/zcode/`（releases/<version>/tar.gz + sha256.txt + latest.json + install.sh）；需 `ZCODE_DIST_BASE_URL` 或 `--base-url`；`--skip-build` 复用产物重组包。
- **统一分发规格**：`specs/zcode-unified-distribution.md` 是统一 Node 发行包的产品规则源文件（v3.15.1 起存在）；实现分三个模块 —— `scripts/zcode-distribution/runner.mjs`（发行包内的 `bin/zcode.mjs` 启动器）、`assets.mjs`（SEA TUI 资产、运行时 node_modules、node-pty prebuild 补齐）、`installer.mjs`（POSIX `sh` 安装脚本生成）。回归在 `scripts/zcode-distribution.test.mjs`（node:test，6 个用例）与 `scripts/zcode-distribution-smoke.mjs`（仓库外解包真机验收）。**与 electron-builder 完全无关**——electron-builder 只服务桌面应用产物（`.exe`/`.dmg`/`.AppImage`/`.deb`），统一分发是独立的 Node 链路（tar.gz + `install.sh`）。两条测试**未接入任何根门禁**，只能手动跑。
- **Windows 原生运行时 Host**：`scripts/windows-runtime-host/` 是 C++ 源码（`main.cpp`、`acceptance.cpp`、安装器进程辅助程序）+ `CMakeLists.txt`（4 个 target，C++17，MSVC `/W4 /utf-8`）；构建入口在 `scripts/build-windows-runtime-host.mjs`（**不在该目录**），产物落 `packages/desktop/bundled-tools/win32-<arch>/runtime-host/`。TS 侧对应模块是 `packages/services/src/windows-runtime-host/`（受管模块，`owner: runtime`）。验收 `host-acceptance.cjs` 是**手工流程**，其 node:test 回归也未接入门禁。

- 原生搜索工具：`pnpm build:native-search` / `pack:native-search`（`scripts/build-native-search-tools.mjs` / `package-native-search-tools.mjs`，跨平台 prebuild 处理见 `prepare-prebuilds*`）；CI 依赖预置用 `ci:ensure-native-search-deps`，端到端验证 `test:native-search:e2e`、`test:sea-runtime-tools:e2e`。

## 第三方与许可

- `third-party/`：声明材料与生成流程。**`third-party/SPEC.md`**（v3.15.1 起存在）是第三方许可材料与发行交付的产品规则与所有者表，`third-party/README.md` 说明用户取得声明的入口与生成状态。
- 脚本分工：`scripts/third-party-npm.mjs`（解析锁文件生产图与实际安装图、读取包内原文）、`scripts/generate-third-party-notices.mjs` 与 `scripts/licenses.mjs notices`（生成 `THIRD-PARTY-NOTICES.md` 与 `inventory.json`）、`scripts/licenses.mjs check [--strict]`（显式许可标识、新鲜度与材料完整性检查）、`scripts/third-party-notices.mjs`（构建期读取与分发声明的唯一入口，各构建入口只调用它，不另建许可数据库）。
- 生产图口径：取所有工作区项目的**生产**依赖（含不发布的内部应用）；构建工具必须放 `devDependencies` 否则会被误算；按 pnpm 在当前宿主上会安装的包过滤（`os`/`cpu`/`libc` 与 `supportedArchitectures`）；pnpm 只在 Linux 宿主检查 `libc`，故 macOS 生成的声明含 glibc 与 musl 两类，是最全集合，正式生成在 macOS 执行。
- 已登记的宽松许可例外：libvips（LGPL，sharp 引入，只以独立可替换动态库分发）、`apps/dev-docs` 的 `elkjs`（EPL-2.0，内部应用独有、不随产品分发）；其余 LGPL/GPL/EPL 等按类别阻断。
- **构建不更新清单，也不隐式运行许可校验**；inventory 过期、待核验项或原生登记不匹配都**不阻断**开发与打包。`readVerifiedNotices(root, { requireComplete: true })` 目前只由显式检查使用；接入 SEA 发布与 SMB 上传前必须先按当前依赖树重新生成声明并关闭缺口，否则这两条发布路径会立即失败。
- **已知未关闭项**：`inventory.json` 的 `reviewRequired` 仍有 **25 项**待补齐的原文与来源证据；`scripts/licenses.mjs check --strict` 在缺口存在时必然失败（当前只作显式命令，未接入 SEA CI 发布与手动 SMB 上传入口）。`node scripts/licenses.mjs notices` / `check` **没有对应的根 npm script**，只能直接跑。
- `scripts/license-texts/` 存 14 个 SPDX 许可全文快照；**当前只有 `Apache-2.0.txt` 被生成器消费**（`scripts/generate-third-party-notices.mjs`，供上游 AI Elements 的短版授权头补全文），其余 13 个是备用的标准条款池，无代码引用也未进 `inventory.json`。
- 交付入口：Desktop（`Resources/THIRD-PARTY-NOTICES.md` + `Resources/licenses/electron/`）、Web（部署根 + HTML `rel="license"`）、Server HTTP / remote bundle、CLI（`dist/THIRD-PARTY-NOTICES.md` 伴随文件）、原生搜索工具（每工具目录 `THIRD-PARTY-NOTICES.txt` + `SOURCES.json`）、远端 Node 组件（`LICENSE.node.txt` + `NODE-SOURCES.json`）、统一分发包（`agent/THIRD-PARTY-NOTICES.md`）。
- 许可 Apache-2.0（根 package.json）；项目声明见 `NOTICE.md`；开源导出树单独按开源依赖树重新生成声明，不沿用闭源声明。

## 日志规范（根 AGENTS.md 摘要）

- UI 用 `packages/ui/src/logger.ts`；Agent/session/runtime 服务日志用 `createServiceLogger(scope)`（`packages/services/src/logger/serviceLogger.ts`）。
- `debug`＝协议原始数据/流式 chunk/逐条工具更新（生产不落盘）；`info`＝进程与会话生命周期、权限结果、一次性初始化；`warn`＝可恢复异常；`error`＝崩溃、握手失败、鉴权丢失。
- 不在日志、示例或提交中写入凭据、真实用户数据和内部服务地址。
